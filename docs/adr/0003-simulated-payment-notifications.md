# ADR 0003: Simulated provider notifications are authenticated observations

The worker simulates provider delivery over HTTP rather than directly confirming bookings, so duplicate, delayed, out-of-order and retried notifications exercise the same transactional boundary. HMAC-SHA256 over the decoded (post-gzip), otherwise unmodified JSON request body authenticates notifications with `PAYMENT_WEBHOOK_SECRET`; this is an internal demo trust boundary, not a real payment integration. Provider event IDs are durable and idempotent: identity is payment attempt plus outcome (provider `occurredAt` is informational), conflicting reuse is 409, and identical redelivery returns duplicate without repeating side effects. The public stream records at most one duplicate observation per provider event and one already-final observation per newly received final-state event; durable bookkeeping bounds replay-driven stream growth.

Attempt states are absorbing (`initiated → succeeded | failed`); processing observations do not finalize them, and any notification after finalization is ignored. PostgreSQL decides live-hold confirmation versus late-success refund under the ownership lock order; after lock waits, the decision also rechecks current seat pointers, not merely the transaction-start deadline. Late success never reclaims inventory. Refund completion commits processing separately from refunded plus its durable completion event, so a crash leaves recoverable processing work. Redis jobs are only best-effort wake-ups after commit: database sweeps recover initiated attempts lacking applied terminal outcomes and pending refunds after queue loss.
